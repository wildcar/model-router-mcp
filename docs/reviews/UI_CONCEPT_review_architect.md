## Вердикт по реализуемости

Концепция реализуема, содержательно правильная и опирается на данные, которые уже лежат в базе. Проверил по коду: `latency_ms`, `finish_reason`, `usage_raw`, `error_message`, `request_ref`, `response_ref`, `cost_source`, `requested_model_id`, `fallback_reason` есть в `request_logs` (`storage/database.py:234-261`), а `list_request_logs` делает `SELECT *` и уже отдаёт их клиенту целиком (`storage/database.py:598-602`, `web/api.py:236-239`). То есть претензия «данные есть, на экране нет» точна, и половина первой волны это работа по рендеру, а не по бэкенду.

Три оговорки к реализуемости.

1. Концепция недооценивает объём серверной работы. Из тринадцати ручек раздела 17 первая волна требует шести, и две из них (`/api/capabilities`, `/api/plan`) требуют изменений в слоях, которые сейчас про UI ничего не знают: `adapters/base.py` и `routing/router.py`. Это не «требование к API», это правка контракта адаптера, а на него есть ADR-0001.
2. Концепция требует «один инспектор в трёх местах», но серверные формы данных для этих трёх мест сегодня разные и по именам полей, и по вложенности. Пока это не сведено к одной схеме на сервере, единый компонент не получится, получатся три маппера в JS.
3. Часть требований (виртуальная таблица, SSE) списана с задач большего масштаба и на этих объёмах не окупается. Подробно ниже.

Скрытая цена, которую документ не называет: без пары починок в существующем коде первая волна выйдет на прод сломанной. Их две, обе P1, обе описаны в разделе рисков: таймаут nginx на длинных прогонах и XSS в журнале.

## Решение по стеку

### Что требует концепция и чего это стоит

| Требование концепции | Реальная сложность на ванили |
|---|---|
| Виртуальная таблица (`UI_CONCEPT.md:511`, `:157`) | Не нужна. 331 строка, страницы по 50 (`:547`). Браузер рисует тысячу `<tr>` без заметной задержки. Виртуализация начинает окупаться от 10 000 строк в DOM |
| Master-detail «Модели» (`:340`) | Три колонки на CSS grid плюс выбранная строка в URL. Дешево |
| Фасеты со счётчиками (`:376`) | Счётчики считает сервер одним `GROUP BY`. На клиенте только рендер списка |
| Просмотрщик JSON (`:298-309`) | Единственный дорогой компонент. Сворачивание, подсветка, поиск, копирование пути: 300-400 строк своими руками |
| Инспектор из шести вкладок в трёх местах (`:508`) | Дорого не в разметке, а в контракте с сервером |
| Состояние в URL (`:510`) | 100-150 строк модуля поверх `URLSearchParams` и `history` |
| SSE (`:537`) | Дорого в инфраструктуре, дёшево в коде. См. раздел 6 |

### Рекомендация

**Остаться на Jinja2 без сборщика. Добавить htmx и Alpine как вендоренные файлы в `static/vendor/`, вынести весь JS из `<script>` в шаблонах в ES-модули под `static/js/`. Решение о переходе на Vite отложить до третьей волны и принимать по факту, а не заранее.**

Обоснование по пунктам.

Сборка сегодня стоит дороже, чем экономит. Прод обновляется `git pull` плюс `pip install` под пользователем `modelrouter` (`deploy/DEPLOY.md:88-95`, ADR-0004). Ввод Vite означает либо node на проде и шаг сборки в `deploy.sh`, либо коммит собранного бандла в репозиторий. Первое ломает простоту юнита и добавляет вторую экосистему в проект, где `AGENTS.md:91` фиксирует питоновский стек, а весь тестовый контур это `pytest`. Второе означает, что бандл и исходники расходятся при любом ручном хотфиксе на хосте.

Нативные ES-модули закрывают главную боль текущего кода без сборщика. Проблема `test.html` не в отсутствии React, а в том, что 206 строк логики живут внутри HTML, не переиспользуются и не тестируются. `import` в браузере решает это сегодня: `<script type="module" src="/static/js/pages/run.js">`, внутри `import {JsonView} from '../components/json-view.js'`. Ценой становится десяток HTTP-запросов на страницу, что за nginx с HTTP/2 несущественно.

htmx снимает 70 процентов работы по таблицам и фильтрам. Пагинация, обновление таблицы при смене фильтра, подстановка карточки в правую панель, отмена предыдущего запроса при быстрой смене фильтров (`hx-sync="this:replace"`), дебаунс (`hx-trigger="keyup changed delay:250ms"`) существуют как атрибуты. Свой код на это ушёл бы примерно на 400 строк. Alpine закрывает локальное состояние без сети: вкладки инспектора, сворачивание блоков, чекбоксы массовых действий. Оба файла порядка 15 КБ, кладутся в `static/vendor/`, версия фиксируется в git.

Свои компоненты остаются только там, где библиотеки не помогают: просмотрщик JSON, таймлайн шагов, горячие клавиши, модуль состояния URL. Это 800-1000 строк за все три волны, обозримо.

### Граница, за которой ваниль перестаёт работать

Три признака. Появление клиентского состояния, которое переживает переход между экранами (например, «Матрица» с четырьмя параллельными прогонами, каждый со своим таймлайном). Появление вычисляемых зависимостей глубже двух уровней (фильтр меняет счётчики, счётчики меняют доступные опции, опции меняют выбранную строку). Появление одного и того же куска UI больше чем в трёх местах с разными данными.

Первый признак наступает в третьей волне на «Матрице». Тогда и решать.

### Цена перехода на Vite позже и как её удержать низкой

Одно правило делает миграцию дешёвой: **`/api/*` остаётся чистым JSON и является стабильным контрактом, HTML-фрагменты для htmx живут отдельно под префиксом `/ui/*`**. Тогда переход на SPA это удаление `web/fragments.py` и шаблонов `partials/`, а вся серверная логика (сериализаторы, фильтры, фасеты) остаётся нетронутой. Без этого правила бизнес-знание расползётся по Jinja-шаблонам и переход станет переписыванием.

Грубая цена вариантов на все три волны, человеко-дни для одного разработчика с агентской поддержкой:

| Вариант | Настройка | Фронт волн 1-3 | Риск сопровождения |
|---|---|---|---|
| Чистая ваниль как сейчас | 0 | 22-28 (2500-3500 строк своего JS) | Высокий: то, чего просили избежать |
| Jinja + htmx + Alpine + ES-модули | 0.5 | 14-18 | Средний, снижается правилом `/ui` против `/api` |
| Vite + Preact/TS с нуля | 2-3 | 16-20 плюс переписывание трёх текущих страниц | Средний, плюс вторая экосистема в деплое |
| Переход на Vite после второй волны | 2-3 | плюс 4-6 на перенос при соблюдении правила `/ui` | Приемлемый |

Разница между вторым и третьим вариантом в первой волне невелика, а вот в стоимости деплоя и в требованиях к тому, кто будет это поддерживать, разница принципиальная.

## Замечания по разделам концепции

Приоритеты: P1 блокирует волну 1, P2 нужно до волны 2, P3 можно отложить или выбросить.

### Раздел 6 и 13. Единая форма данных для инспектора. P1

Сейчас одни и те же сущности приезжают в браузер в двух разных формах.

- Ответ прогона: `dispatch_summary` (`mcp_server/serialize.py:115-133`) даёт `provider`, `model_id`, вложенный `usage`, `cost_usd`, `cost_source`, `log_id`.
- Строка журнала: `dict(row)` (`storage/database.py:602`) даёт `service_provider_id`, `model_id`, плоские `prompt_tokens`/`completion_tokens`, `usage_raw` строкой JSON, `created_at`, `error_message`.

Разные имена для одного и того же (`provider` против `service_provider_id`), разная вложенность токенов, `usage_raw` в одном месте объект, в другом строка. Если инспектор писать поверх этого, в JS появятся два маппера, и обещание «один компонент, три места» (`UI_CONCEPT.md:508`) не выполнится.

Что делать: завести `router_mcp/web/views.py` с функциями `run_view(result: DispatchResult) -> dict` и `run_view_from_log(row: dict) -> dict`, обе возвращающие одну схему с полями `status`, `model`, `requested_model`, `fallback_reason`, `usage`, `cost`, `latency_ms`, `finish_reason`, `refs`, `raw`, `log_id`. Инспектор принимает ровно её. Тест на равенство ключей у обеих функций стоит десять строк и защищает контракт навсегда.

Заодно закрывается дыра: `dispatch_summary` не возвращает `latency_ms` и `finish_reason`, хотя оба вычисляются в `routing/router.py:368` и `:403` и пишутся в лог. Экран «Прогон» в концепции показывает задержку в нулевом уровне (`UI_CONCEPT.md:139`), а сервер её не отдаёт.

### Раздел 5. Матрица релевантности. P1

Утверждение концепции, что матрица должна приезжать с сервера (`UI_CONCEPT.md:130`), верное. Важно, откуда сервер её берёт. Правильный источник это сами адаптеры: `openrouter.py:66` читает `temperature`, `max_tokens`, `top_p`, `reasoning`; `deepseek.py:59` те же без `reasoning`; `claude_api.py:62,69` плюс дефолт `max_tokens`; `elevenlabs.py:65,72` читает `voice` и `language`; `claude_cli.py:50,51,56` читает `cwd`, `timeout_sec`, `model`; `codex_cli.py:50,51` только `cwd` и `timeout_sec`; `deepgram.py` и `codex_image.py` из `params` не читают ничего. Матрица в концепции (`UI_CONCEPT.md:114-122`) коду соответствует, я сверил построчно.

Если `/api/capabilities` соберут вручную в `web/`, она разойдётся с кодом на первом новом адаптере, ровно как предупреждает сама концепция. Правильно: добавить в `ProviderAdapter` атрибут `SUPPORTED_PARAMS: tuple[str, ...]`, использовать его и в адаптере при сборке payload, и в `/api/capabilities`. Тогда рассинхрон физически невозможен. Это правка контракта адаптера, то есть нужна приписка к ADR-0001 или новый ADR.

### Раздел 5 и 9.1. Разбор `model_id` на клиенте. P1

`vendorOf`, `baseOf`, `variantOf` в `test.html:94-109` режут `model_id` по `/` и `:`. При этом `model_provider` уже лежит отдельной колонкой в БД (`storage/database.py:207`) и уже отдаётся в `model_to_dict` (`mcp_server/serialize.py:17`). Клиент дублирует серверное знание и в одном случае его игнорирует.

Что уезжает на сервер: разбор идентификатора, дерево для каскада (поставщик, вендор, база, вариант) со счётчиками в узлах, фасеты и их счётчики, фильтрация и сортировка списков, текстовое объяснение плана маршрутизации, генерация команды curl (`UI_CONCEPT.md:307`), потому что она обязана знать форму эндпоинта.

Что остаётся на клиенте: форматирование чисел и дат, сворачивание узлов JSON, сортировка уже загруженной страницы, вкладки, горячие клавиши, локальные черновики формы.

### Единицы цены. P2

Конверсия `$/1M` живёт в двух местах: `static/app.js:21-23` (чтение) и `registry.html:194-195` (запись, деление на 1e6). PATCH из концепции (`UI_CONCEPT.md:377`) добавит третье. Решение: канон в API остаётся ценой за токен, к нему в `model_to_dict` добавляются готовые `prompt_price_per_1m` и `completion_price_per_1m`, а PATCH принимает поля с суффиксом `_per_1m` явно. Клиент перестаёт умножать.

Побочно: `PRICE_KIND_LABEL` в `registry.html:113-119` перечисляет пять видов, включая `unknown`, а схема ставит по умолчанию `estimate` (`storage/database.py:226`) и `_row_to_model` подменяет NULL на `estimate` (`:147`). Вид `unknown` ставят только адаптеры без цен (`claude_api.py:113`, `deepseek.py:105`). Перечень видов должен приезжать в `/api/capabilities`, подписи остаются в клиенте как UI-текст.

### Раздел 11. Правка цены каталожной строки. P1, и вопрос 3 концепции закрывается кодом

Концепция утверждает, что каталожную строку отредактировать нельзя (`UI_CONCEPT.md:377`). На самом деле хуже: `POST /api/registry/models` с существующей парой `service_provider_id` плюс `model_id` попадает в `ON CONFLICT DO UPDATE` (`storage/database.py:390`) и переписывает всю строку значениями из тела запроса. Дубликат не создаётся, вместо этого затираются `context_length` (в теле по умолчанию 0, `web/api.py:90`), `deprecated_at` и `last_seen_at` (в `_model_to_row` они берутся из объекта, где `None`, `:110-112`), а снятая модель воскресает как активная (`is_active=1` по умолчанию в `RegistryModel`). То есть текущий путь правки цены разрушительный, просто это никто не замечал.

Отвечаю на вопрос 3 из раздела 21. Не нужен ни отдельный слой наложений, ни смена `source` на `manual`. Достаточно одной строки в `registry/service.py:155`:

```
prices_authoritative = fresh.price_source_kind == "api" and old.source != "manual"
```

Здесь защита ручной цены завязана на `source`, а не на происхождение цены. Если поменять условие на `old.price_source_kind != "manual"`, то `PATCH` сможет менять только `prompt_price`, `completion_price`, `price_source`, `price_source_kind='manual'`, `price_checked_at`, оставляя `source='catalog'` как есть, и следующая синхронизация цену не тронет. Модель данных не усложняется.

Важное следствие, которого нет в концепции: сегодня ручная строка у поставщика с каталогом снимается при первой же синхронизации, потому что цикл деприкации (`registry/service.py:140-144`) не исключает `source='manual'`. Экран «Модели» с кнопкой «Добавить» это воспроизведёт. Либо исключать manual из деприкации, либо явно показывать оператору, что ручная строка для каталожного поставщика живёт до следующей синхронизации.

### Раздел 13. Журнал. P1

`GET /api/logs` отдаёт `SELECT *`, то есть `response_text` до 4000 символов (`routing/router.py:43`), `usage_raw` и `request_text` для каждой из 50-100 строк. Страница журнала при этом рисует 60 символов запроса (`logs.html:58`). На пятидесяти строках это сотни килобайт трафика ради таблицы, которой нужны id, время, пользователь, модель, статус, токены, цена. Список обязан проецировать колонки, а тяжёлое отдавать `GET /api/logs/{id}`.

Фильтры первой волны (`UI_CONCEPT.md:530`) упрутся в индексы. Есть `idx_request_logs_user(external_user_id, created_at)` и `idx_request_logs_provider(service_provider_id, created_at)` (`storage/database.py:266-267`). Фильтр по `status`, `modality`, `model_id`, по наличию подстановки и по `cost_source` пойдёт полным сканом. Нужен `idx_request_logs_created(created_at DESC)` и составной по `(status, created_at)`. На нынешних объёмах разницы не будет, на десятках тысяч строк будет.

### Раздел 9.4 и 17. Долгие прогоны и статус `running`. P2, ответ на вопрос 5 концепции

Держать в памяти процесса достаточно, но не как единственное хранилище. Предлагаю реестр прогонов в `AppCore`: `POST /api/runs` возвращает `run_id` сразу, `GET /api/runs/{id}` отдаёт текущее состояние и накопленные шаги, `DELETE /api/runs/{id}` отменяет. Клиент опрашивает раз в секунду. Это закрывает прогресс, отмену и переживание закрытия вкладки без SSE, без изменений в nginx и без изменений схемы.

Перезапуск процесса такой прогон теряет. Для CLI, который идёт до 1800 секунд (`config.py:96`), это ощутимо, поэтому только для `cli` имеет смысл писать строку лога со `status='running'` до вызова и обновлять её после. Колонка `status` уже есть (`storage/database.py:241`), нужен метод `update_request_log`, схема не меняется. Ставить это в первую волну не надо.

### Раздел 10. Матрица. P3, ответ на вопрос 2 концепции

Отдельный экран не нужен. Это режим «Прогона» с мультивыбором моделей: тот же блок запроса, вместо одного `model_id` список чипов, вместо одной карточки результата таблица со строками, клик по строке открывает тот же инспектор. Отдельный экран означает дубль всей левой колонки формы. В навигации пункт можно оставить, он будет ссылкой на `/run?models=a,b,c`.

`POST /api/runs/batch` (`UI_CONCEPT.md:538`) при этом не нужен: N обычных `POST /api/runs` из браузера дают то же самое, плюс частичные результаты по мере готовности, плюс отмену по одному. Серверный batch добавляет ручку и ничего не упрощает.

### Раздел 16. Компоненты. P2

Список компонентов правильный. Не хватает двух вещей.

Версионирование контракта. Прод обновляется рестартом сервиса (`deploy/DEPLOY.md:88`), а браузер держит закешированные `/static/app.js` и `/static/app.css`: `base.html:7,23` ссылается на них без параметра версии, `app.py:127` монтирует `StaticFiles` без правил кеширования. После деплоя оператор получит старый JS против нового API и молчаливые ошибки. Лечится двумя строками: `?v={{ version }}` в `base.html` из `router_mcp.__version__` плюс поле `schema_version` в `/api/capabilities`, которое клиент сверяет при загрузке и при расхождении показывает баннер «обновите страницу».

Общий слой. В `static/js/core/` уезжают `api.js` (текущий `app.js:2-16` плюс `AbortController`), `state.js` (URL), `format.js` (числа, деньги, длительности, даты в одном месте), `dom.js` (безопасное создание узлов), `keys.js` (горячие клавиши). В `components/` уезжают `json-view.js`, `inspector.js`, `kv-table.js`, `chips.js`, `facets.js`, `timeline.js`. Правило: компонент не знает про `fetch` и не знает про URL, он принимает данные и отдаёт события.

### Раздел 8. Семь пунктов навигации. P3, ответ на вопрос 1 концепции

Семь много для одного оператора, но проблема не в числе, а в том, что три пункта из семи это разные срезы одних данных. Предлагаю пять: Обзор, Прогон, Модели, Журнал, Поставщики. «Матрица» становится режимом «Прогона», «Расход» становится вкладкой на «Журнале» (те же фильтры по периоду и пользователю, другой рендер). Экономия примерно два дня разработки и один экран в голове оператора.

### Раздел 9.2. Показывать план всегда или по кнопке. P2, ответ на вопрос 4

По кнопке. Автоматический пересчёт при каждом изменении формы это запрос на каждое нажатие клавиши в поле `model_id`, при том что `plan()` ходит в БД дважды (`routing/router.py:120` и `:243`). Компромисс: пересчитывать автоматически только при изменении дискретных полей (модальность, поставщик, политика подстановки), с дебаунсом 300 мс, а по кнопке показывать полную таблицу кандидатов.

### Раздел 21, вопрос 7. Показывать ли payload провайдера. P2

Показывать тело, не показывать заголовки. Ключи живут только в заголовках (`adapters/base.py` и конкретные адаптеры собирают их при создании клиента), тело `payload` в `openrouter.py:64` и `deepseek.py:57` ключей не содержит. Правило: в `run_view` попадает только тело, заголовки не сериализуются вообще, чтобы не строить фильтр редактирования, который однажды пропустит новый заголовок.

### Раздел 21, вопрос 6. Светлая тема. P3

Отложить. Одна инсталляция, один оператор. Достаточно завести токены цветов в `static/css/tokens.css` через CSS-переменные (задел уже есть в `app.css:1`), тогда светлая тема позже это один блок `@media (prefers-color-scheme: light)`.

## Архитектура состояния и URL

Единый источник истины по всему, что можно послать коллеге ссылкой, это строка запроса.

```
/logs?status=error&user=bot-77&since=24h&model=deepseek-chat&sel=4821&tab=raw
/models?q=deep&modality=chat&price=estimate,unknown&sel=deepseek%2Fdeepseek-chat
/run?modality=chat&model=deepseek-chat&from_log=4821
```

Правила.

1. В URL живут: все фильтры, поиск, страница, сортировка, выбранная строка (`sel`), активная вкладка инспектора (`tab`). Это ровно то, что требует концепция в приёмке про deep link и в разделе 16 про «сохранение в URL» (`UI_CONCEPT.md:510`).
2. В URL не живут: живой хвост, состояние сворачивания узлов JSON, черновик промпта, выбор темы. Живой хвост и тема в `localStorage`, черновик в `sessionStorage` по ключу экрана.
3. `pushState` для дискретных действий (клик по фасету, выбор строки), `replaceState` для набора текста. Иначе кнопка «Назад» отматывает по одной букве.
4. Первый рендер делает сервер. Сейчас `pages.py:17-29` игнорирует параметры запроса и всегда отдаёт пустой каркас, из-за чего после F5 экран моргает пустотой и потом дозагружается. Страницы должны читать `request.query_params` и отдавать первую страницу таблицы уже заполненной. С htmx это естественно, дальше он же обновляет фрагменты.
5. Модуль `core/state.js` предоставляет `read()`, `patch(obj)`, `subscribe(fn)` и умеет сериализовать множественный выбор фасетов в один параметр через запятую. Никакой другой код с `history` не работает.
6. Восстановление после перезагрузки на «Прогоне»: результат последнего прогона не восстанавливается из формы, он восстанавливается по `log_id`. То есть после отправки в URL кладётся `?log=4821`, и перезагрузка страницы поднимает инспектор из журнала. Это же бесплатно даёт сценарий С8 (повтор запроса) и убирает необходимость держать результат в `sessionStorage`.

## Производительность и объём

Считаю по реальным цифрам.

- `GET /api/models` при 331 модели и примерно 20 полях на строку это 120-180 КБ JSON. `test.html:282` перезагружает его при смене tier, `:204` при смене модальности. Нужно: кеш в памяти на сессию по ключу «модальность плюс tier», `ETag` на эндпоинте, и отказ от перезагрузки при смене tier (фильтровать уже загруженное).
- Реестр на тысяче строк: страницы по 50, серверная фильтрация и сортировка. Виртуализацию не делать. Если когда-нибудь понадобится показать все строки разом, это `content-visibility: auto` на `<tr>`, одна строка CSS, а не виртуализатор.
- Журнал: проекция колонок в списке (см. выше), `LIMIT/OFFSET`, `COUNT(*)` отдельным полем ответа. Для живого хвоста не опрос всей страницы, а `GET /api/logs?since_id=N`, который отдаёт только новые строки.
- Отмена запросов: `AbortController` на каждый вид запроса, хранится в модуле страницы, при новом запросе того же вида предыдущий отменяется. На htmx это `hx-sync`. Дебаунс 250 мс для текстовых полей, 0 для чекбоксов и селектов.
- Большие ответы: `response_text` в базе обрезан до 4000 символов (`routing/router.py:43`), так что «сотни килобайт» (`UI_CONCEPT.md:550`) в журнале физически не появятся, они появятся только в свежем прогоне. Порог схлопывания ставить на 8 КБ текста и на 256 КБ JSON, не на мегабайт: подсветка синтаксиса на мегабайте вешает вкладку.
- Блобы: `serve_blob` (`web/api.py:358-367`) читает файл целиком в память и отдаёт `Response` без `Cache-Control` и без поддержки `Range`. Ref это `<uuid>.<ext>` (`blobs/store.py:26-30`), то есть содержимое по ссылке неизменно. Меняем на `FileResponse` с `Cache-Control: public, max-age=31536000, immutable`. `FileResponse` умеет `Range`, аудиоплеер начнёт перематывать без перезакачки. Это три строки и заметная разница на экране «Прогон» с tts.

## SSE и стриминг за nginx

Здесь у концепции недооценён риск, и есть готовая к срабатыванию проблема в текущем проде.

`location /mcp` настроен правильно: `proxy_buffering off`, `proxy_read_timeout 3600s` (`deploy/nginx-model-router.conf:20-32`). `location /` (`:41-49`), под который попадает весь `/api/*`, не имеет ни того, ни другого. Значит для API действует умолчание nginx `proxy_read_timeout 60s`, и буферизация включена.

Отсюда следствие, не зависящее от концепции: **`POST /api/cli` на проде отваливается по 504 через 60 секунд**, хотя `CLI_RUN_TIMEOUT_SEC` равен 1800 (`config.py:96`), а прогоны в примерах концепции идут по 412 секунд (`UI_CONCEPT.md:437`). Процесс при этом продолжает работать, запись в журнал появится, а оператор увидит ошибку шлюза. Это P1, чинится до любой работы по UI.

Что нужно в конфиге для длинных запросов и для потоков:

```
location ~ ^/api/(cli|runs|events) {
    auth_basic "Model Router";
    auth_basic_user_file /etc/nginx/model-router.htpasswd;
    proxy_pass http://model_router;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
    ...
}
```

Плюс приложение должно отдавать `X-Accel-Buffering: no` на потоковых ответах, это страховка на случай, если конфиг на хосте разойдётся с репозиторием.

Подводные камни, специфичные для этого проекта.

- Один воркер и одно соединение с SQLite (ADR-0004, `storage/database.py:156`). Открытое SSE-соединение это задача в event loop, не поток, десяток вкладок процесс переживёт. Но обработчик потока не должен держать `_write_lock` между отправками событий.
- Промежуточные прокси и антивирусы иногда буферизуют `text/event-stream` независимо от nginx. Лечится периодическим комментарием-пингом раз в 15 секунд.
- `EventSource` не умеет слать заголовки. За Basic-авторизацией это работает, потому что браузер подставляет учётку сам, но если авторизацию когда-нибудь заменят на Bearer, `EventSource` придётся менять на `fetch` с `ReadableStream`.
- FastMCP уже держит свой session manager в том же процессе (ADR-0003). Добавление второго механизма долгоживущих соединений увеличивает шанс, что рестарт сервиса подвесит выгрузку. `Restart=always` это прикроет, но при отладке будет путать.

Вывод: **SSE в третьей волне не делать вообще**. Живой хвост журнала это `GET /api/logs?since_id=N` раз в 3 секунды, что концепция и сама допускает (`UI_CONCEPT.md:548`). Таймлайн долгого прогона это опрос `GET /api/runs/{id}` раз в секунду. Оба варианта работают через текущий nginx без единой правки, переживают рестарт клиента и не требуют логики переподключения. SSE вернуть в план, только если появится требование, которого опрос не закрывает (например, десятки одновременных наблюдателей).

## Риски

**P1. Прод уже роняет длинные прогоны.** `location /` без `proxy_read_timeout` (`deploy/nginx-model-router.conf:41-49`) даёт 60 секунд на `/api/cli` при лимите адаптера 1800 (`config.py:96`). Концепция строит на этом сценарий С9. Чинить до начала работ.

**P1. XSS в консоли, работающий уже сегодня.** `logs.html:55-58` подставляет `request_text`, `model_id`, `fallback_reason` и `external_user_id` в `innerHTML` с экранированием только кавычек. `request_text` пишется из любого запроса, пришедшего в MCP или в API, а `external_user_id` по правилу `AGENTS.md:85` это неаутентифицированный свободный ввод. Basic-авторизация защищает от посторонних, но не от полезной нагрузки, которую сам сервис записал в базу. Концепция многократно увеличивает поверхность: полный текст ответа, тексты ошибок, `usage_raw`, отчёты синхронизации. Правило «никакого `innerHTML` с данными» надо ввести до, а не после.

**P1. Разъезжающиеся формы данных.** Описано выше. Если инспектор начнут писать раньше `views.py`, обещание единого компонента не выполнится, и это выяснится на третьем экране, когда переписывать дорого.

**P2. Матрица релевантности как копия.** Если `/api/capabilities` соберут руками в `web/`, она разойдётся с адаптерами. Ровно тот дефект, от которого концепция уходит.

**P2. Правка цены через существующий POST разрушительна.** `web/api.py:318-347` плюс `storage/database.py:381-396` затирают `context_length`, `deprecated_at`, `last_seen_at` и воскрешают снятую модель. Пока нет `PATCH`, экран «Модели» с кнопкой «Сохранить» это ухудшение, а не улучшение.

**P2. Ручные строки у каталожных поставщиков снимаются при синхронизации.** `registry/service.py:140-144` не исключает `source='manual'`. Экран, приглашающий добавлять модели вручную, сделает эту особенность массовой.

**P2. Кеш статики против рестарта.** `base.html:7,23` без версии плюс рестарт по `deploy.sh` дают старый клиент против нового API.

**P2. Payload провайдера и секреты.** `UI_CONCEPT.md:534` и вопрос 7. Решается запретом на сериализацию заголовков, а не фильтром по именам.

**P3. Изменения схемы БД.** Первой волне схема не нужна вообще, нужны только индексы. Второй волне тоже. Третьей нужны `update_request_log` (без DDL) и хранение шагов плана (новая таблица, правка ADR-0002). Механизм добавления колонок в развёрнутую базу уже есть (`storage/database.py:276-309`), новую таблицу он не покрывает, `CREATE TABLE IF NOT EXISTS` в `init()` покроет.

**P3. Инварианты проекта.** Проверил `AGENTS.md:83-87`. Концепция ничего не ломает при условии: сериализаторы и матрица не попадают в `domain/`; экспорт и «сырьё» не приводят к записи бинарных данных в SQLite (крупные payload сохранять через `blobs/store.py`); опрос прогонов не создаёт второго процесса и не трогает `mcp.session_manager`; `external_user_id` в фильтрах и автодополнении остаётся ключом группировки, а не признаком доступа.

**P3. Деплой.** При выбранном стеке `deploy.sh` не меняется вообще: всё лежит в репозитории как статика. Это одна из главных причин выбора.

## Рекомендации по приоритету

1. Починить `location /` в nginx перед любой работой по UI, иначе сценарий С9 не заработает ни в какой волне.
2. Ввести `dom.js` и запретить `innerHTML` с данными, переписать три текущих шаблона на него. Полдня, закрывает работающий XSS.
3. Сделать `web/views.py` с единой формой прогона до того, как будет написана первая строка инспектора. Тест на совпадение ключей обеих функций.
4. Взять стек Jinja2 плюс htmx плюс Alpine плюс ES-модули без сборки. Развести `/api/*` (JSON, стабильный контракт) и `/ui/*` (HTML-фрагменты), чтобы возможный переход на Vite остался переносом слоя представления.
5. Выбросить виртуальную таблицу, SSE, `POST /api/runs/batch` и отдельные экраны «Матрица» и «Расход». Экономия 5-7 дней без потери сценариев приёмки.
6. Собирать `/api/capabilities` из `SUPPORTED_PARAMS` адаптеров, а не из руками написанной таблицы в `web/`. Оформить припиской к ADR-0001.
7. Перевести `GET /api/logs` на проекцию колонок и добавить `GET /api/logs/{id}` и индексы под фильтры до того, как появятся фильтры в UI.
8. `PATCH /api/registry/models`, меняющий только цену и её происхождение, плюс правка условия в `registry/service.py:155`, чтобы ручная цена переживала синхронизацию без смены `source`.
9. Сделать URL единственным источником истины по фильтрам и выбранной строке с самого первого экрана: дописать это позже дороже втрое.
10. Долгие прогоны решать реестром прогонов и опросом, а не стримингом. Отмена, прогресс и переживание закрытия вкладки получаются без единой правки в nginx.

## Тестируемость и доступность

**Тесты.** Сейчас фронт не тестируется никак, весь контур это `pytest` (`AGENTS.md:97`). Предлагаю три уровня, в порядке отдачи на вложенный час.

1. Контрактные тесты на сервере, `pytest`, без браузера. Совпадение ключей `run_view` и `run_view_from_log`. Совпадение `/api/capabilities` с `SUPPORTED_PARAMS` каждого адаптера. Фильтры и счётчики фасетов. Это ловит большинство поломок, потому что почти вся предметная логика уезжает на сервер по решению выше. Пишутся в существующем стиле `tests/test_web.py` с модульным `TestClient` (ограничение одной FastMCP на процесс, ADR-0003, уже учтено в фикстуре `tests/test_web.py:18-36`).
2. Playwright с `pytest-playwright`, восемь-десять сценариев ровно по разделу 19 концепции. Один браузер, один прогон приложения с подставными адаптерами. Появляется во второй волне, раньше нечего проверять.
3. Юнит-тесты чистых JS-функций (`format.js`, разбор состояния URL). Без npm их запускать нечем, поэтому либо не писать вовсе, либо держать эти функции такими, чтобы их поведение проверялось через Playwright. Я за первое: не заводить вторую тестовую экосистему ради двадцати строк.

**Доступность.** Ограниченный, но обязательный набор.

- Таблицы делать настоящими `<table>` с `<th scope="col">`, а не сеткой из `<div>`. Screen reader на моноширинной таблице читает только то, что размечено; выравнивание через `tabular-nums` (`app.css:29`) семантики не даёт.
- Числовые ячейки: видимое значение округлено, точное лежит в `title` и в `aria-label`. Концепция это требует (`UI_CONCEPT.md:505`), реализация обязана дать и то, и другое.
- Чипы статусов не должны кодировать смысл одним цветом. `ok` зелёный плюс слово, `error` красный плюс слово. Пульсирующий синий для `running` (`UI_CONCEPT.md:504`) обернуть в `@media (prefers-reduced-motion: reduce)`.
- Контраст: текущая палитра `--muted:#9aa3af` на `--card:#1a1d24` (`app.css:1`) даёт примерно 7:1, это проходит. Планируемый `--muted-2` (`UI_CONCEPT.md:515`) легко уедет ниже 4.5:1, порог надо проверить при вводе токенов, а не после.
- Клавиатура: концепция обещает горячие клавиши (`UI_CONCEPT.md:517`), но не обещает фокус. Обязательны видимый `:focus-visible`, ловушка фокуса в выезжающей карточке журнала, возврат фокуса на строку таблицы при закрытии по `Esc`, и отключение односимвольных клавиш, когда фокус в поле ввода.
- Выезжающая карточка это `<dialog>` или блок с `role="complementary"` и `aria-live="polite"` на итоговой строке результата, чтобы завершение прогона было слышно.
- JSON-просмотрщик: узлы дерева как `<details>`/`<summary>` там, где это возможно. Бесплатно даёт клавиатуру, семантику раскрытия и поиск браузером.
